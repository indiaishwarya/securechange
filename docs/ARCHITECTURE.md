# SecureChange architecture

## Purpose

SecureChange analyzes repository changes before deployment. It combines deterministic Git and source analysis, dependency and schema impact analysis, retrieval-grounded explanations, and security scanning in one review surface.

## System shape

```text
React dashboard -> FastAPI API -> analysis services
                         |              |
                         v              v
                  PostgreSQL/pgvector  Git, Bandit, Semgrep
```

The dashboard is a Vite-built React/TypeScript application. The API is a stateless FastAPI service. PostgreSQL stores repository metadata, parsed artifacts, embeddings, findings, and scan history. Git is read-only input for local repository analysis. Bandit and Semgrep are optional external analyzers; built-in checks remain available when they are absent or time out.

## Request flow

1. A repository is inspected and its tracked files, commits, symbols, OpenAPI operations, and metadata are persisted.
2. Two commits are compared using Git diff and function context.
3. OpenAPI contracts, changed symbols, dependency edges, and schema changes are analyzed.
4. Repository evidence is chunked, embedded with a deterministic 384-dimensional feature-hash embedding, searched with BM25 and vector similarity, and reranked.
5. Security findings are generated by built-in checks and optional Bandit/Semgrep results, then enriched with retrieved evidence and an optional LLM explanation.
6. Findings and scan summaries are persisted for history and displayed in the dashboard.

## Main API groups

- `/health`, `/ready`, `/metrics`: liveness, database readiness, and lightweight operational metrics.
- `/api/v1/repositories/*`: inspection, commit comparison, impact analysis, retrieval, security scanning, and history.
- `/api/v1/github/*`: GitHub repository inspection and pull-request comments.
- `/api/v1/evaluation/benchmark`: intentional-bug benchmark metrics.

## Data model

Core tables are `repositories`, `repository_commits`, `repository_files`, `source_symbols`, `api_endpoints`, `pull_requests`, `knowledge_chunks`, `security_findings`, and `scan_history`. `knowledge_chunks.embedding` uses pgvector. The schema is idempotently created by the API and initialized by `infra/db/init.sql` for Docker deployments.

## Reliability and security decisions

- Every request receives an `X-Request-ID`; response time and status are exposed in headers.
- `/health` does not require the database, while `/ready` verifies database connectivity.
- Validation and unexpected failures return consistent JSON error envelopes without exposing exception details to clients.
- Git commands use argument arrays, bounded timeouts, and no shell interpolation.
- Secrets are provided through environment variables and excluded from Git.
- Expensive analyzers have bounded timeouts and their status is returned explicitly.

## Deployment

The repository includes production-oriented Dockerfiles and `docker-compose.production.yml`. Run it behind TLS and a reverse proxy in a real environment, replace the default database password, and provide `GITHUB_TOKEN` and `OPENAI_API_KEY` only when those integrations are needed. See `docs/RUNBOOK.md` for operations and troubleshooting.
